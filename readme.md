# 面向 CS / Robotics 研究的 Codex 配置

[English](README.en.md) | 简体中文

这套配置来自一名计算机科学与机器人方向的 PhD 学生，日常用于论文复现、实验代码开发和调试。目标是在优先保证代码正确性与研究可复现性的前提下，保持代码干净、简洁，并通过 GPT-6.1 Sol、GPT-6.1 Terra 与 GPT-6 Luna 的任务分工减少额度消耗。

## 文件说明

- [config.toml](config.toml)：主模型、推理强度、子代理并发及通用偏好设置。
- [AGENTS.md](AGENTS.md)：最小修改、研究语义保护、精简记录、验证和委派规则。
- [agents/](agents/)：各子代理的模型与职责边界；权限继承自主会话。

## 模型与任务分工

| 角色 | 模型 / 推理强度 | 职责 |
| --- | --- | --- |
| 主代理 | GPT-6.1 Sol / medium，Plan 模式 high | 规划、架构与科学决策、处理歧义、任务委派和最终验收 |
| `scout` | GPT-6 Luna / high | 只读检索代码、配置、文档和日志，返回关键证据 |
| `quick_implementer` | GPT-6 Luna / high | 实现已决定、范围明确的局部修改，执行针对性验证 |
| `system_implementer` | GPT-6.1 Terra / high | 按明确实现契约完成方案已确定、工作量较大且适合隔离实施上下文的任务，包括模块交互、集成路径和较大量的验证工作；发现证据与契约冲突时交回主代理 |
| `debugger` | GPT-6.1 Sol / high | 复现非显然故障，先定位根因；修改代码需主代理明确委派 |
| `reviewer` | GPT-6.1 Sol / high | 只读审查具体的正确性、回归或研究语义风险 |

未指定角色的子代理默认使用 GPT-6.1 Sol / medium；手动 `/review` 使用 GPT-6.1 Sol。配置显式启用 Multi-Agent V2，并发上限为两个子代理线程，不包含主代理。Luna 不承担架构、算法或实验方法决策，任务超出边界时停止并交回主代理，由主代理决定直接处理或委派给 `system_implementer`。

`system_implementer` 使用 Terra / high 的前提是主代理已明确方案、约束和验收标准。官方[模型选择指南](https://developers.openai.com/api/docs/guides/model-selection)将 Terra 推荐用于范围明确的代码修复等任务，并建议在相同输入和推理强度下与 Sol 比较。这不能直接证明 Terra 适合所有大型集成任务；当前保留该默认分工，复杂集成可由主代理使用 Sol 完成，后续根据实际质量、返工和用量决定是否调整。尚未通过本项目的同任务模型对比验证。

## 配置思路

- **代码保持精简**：优先复用已有实现和依赖，只做必要的局部修改，沿用现有模块边界。按实际职责和复用需求拆分，避免为减少行数牺牲可读性，或为形式上的结构化增加文件和层级。
- **研究语义优先**：复现时保留参考算法、数值行为和相关依赖版本；不擅自改变坐标系、单位、归一化、数据划分、指标、随机种子或实验协议。有实质歧义时先查证或询问。
- **按需委派以节省额度**：仅在上下文隔离、专门分工或独立工作带来的收益足以抵消额外成本时委派。明确的局部任务交给 Luna，较大的已批准实现可交给 `system_implementer`；与未解决科研或架构决策紧密耦合的实现留在主代理。通常只启用一个子代理，仅对真正独立的工作使用第二个，最多两个，避免重叠修改。
- **减少上下文与重复创建**：委派任务包含目标、已决定的约束、相关文件、验收标准和必要验证。工具支持 `fork_turns` 时显式设置，默认使用 `"none"`，仅在必要时使用 `"all"`；有限历史继承仅使用工具实际支持的选项。相关后续任务通过当前工具的后续任务机制复用已有代理，子代理未经主代理授权不得继续创建子代理。
- **验证与风险匹配**：执行最小但足够的测试、构建或烟雾检查，不默认运行全套测试；仅在存在具体未解决风险时增加审查。数值行为变化时按项目定义的容限检查参考输出或不变量，不能仅凭程序成功退出判断科研正确性。
- **控制实验成本**：小型定向测试可自动执行；昂贵训练、大规模仿真、多种子实验、参数扫描、大量下载和真实硬件操作需明确授权。资源预算在具体项目或任务中约定，授权范围及预算内连续推进，扩大范围或超预算时再确认。

## 实验记录与交接

按需复用和更新已有记录，只保留其他 agent 理解当前状态、定位证据并继续工作所需的信息，不强制模板或额外文件；具体规则统一见 [Documentation and handoff](AGENTS.md#documentation-and-handoff)。

## 安装与加载检查

本仓库是配置模板，根目录的配置文件不会因打开仓库而自动成为项目配置。个人使用时，将 [config.toml](config.toml)、[AGENTS.md](AGENTS.md) 和 [agents/](agents/) 按原有相对路径合并或复制到 Codex 用户目录（默认 `~/.codex/`，设置 `CODEX_HOME` 时以其为准），保留 `agents/` 子目录及已有个人配置。仅项目使用时，配置及角色文件按同样目录结构放在受信任项目的 `.codex/` 下，项目指令放在项目根目录；具体项目的运行命令和资源预算也放在项目级指导中。[官方配置加载指南](https://learn.chatgpt.com/docs/config-file/config-basic)

修改后启动新会话，检查所选模型、推理强度、可用角色和实际权限，并请 agent 概括已加载的指令。CLI 可使用 `/status` 和 `/debug-config` 核对；IDE 和桌面端以当前会话设置为准。命令行或宿主覆盖可能改变配置默认值，字段可解析不代表已在每个客户端生效。

子代理继承主会话权限，自定义角色文件的 `sandbox_mode` 不会建立独立沙箱。`scout` 和 `reviewer` 的“只读”是行为约束；需要强制只读时，应在主会话选择相应权限。日常开发可在主会话选择 `workspace-write` 与 `on-request`，工作区内允许的操作无需逐次确认。[官方子代理权限说明](https://learn.chatgpt.com/docs/agent-configuration/subagents#approvals-and-sandbox-controls)

这是一套可供参考的研究工作流通用配置。[config.toml](config.toml) 已移除个人 MCP、本机绝对路径，以及依赖本机安装位置的插件市场和插件配置。MCP 和插件在本机单独配置；桌面外观选项属于客户端偏好。`[windows]` 为 Windows 专用设置，其他系统可省略。当前保留 `elevated`，MXC 升级需单独确认兼容性，尤其是后台实验进程的生命周期。[官方 Windows 沙箱指南](https://learn.chatgpt.com/docs/windows/windows-sandbox)
